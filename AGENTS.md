# Правила учебной разработки

- Работать небольшими этапами по `docs/SPECIFICATION.md`. Не добавлять функции следующих этапов без необходимости для текущей задачи.
- Писать интерфейс, пояснения и документацию на русском языке.
- Добавлять русские docstring к модулям, классам и функциям: назначение, параметры, результат и ожидаемые ошибки, если они есть.
- Подробно объяснять нетривиальные действия и причины решений комментариями. Комментарии должны соответствовать текущему коду и помогать начинающему разработчику.
- Отделять генерацию, оценку и хранение от Tkinter. Не создавать лишние абстракции только ради архитектуры.
- Использовать `secrets` для генерации секретов. Не писать собственные криптографические алгоритмы.
- Не сохранять реальные пароли, ключи и хранилища в репозиторий, журналы и отчёты. Тестировать на искусственных данных.
- Добавлять содержательные тесты к генерации, оценке, шифрованию и хранению. Для простых изменений документации и оформления отдельные тесты не нужны.
- После этапа сообщать, что реализовано, какие проверки реально выполнены и что пользователю проверить вручную.
- Не заявлять готовность будущих функций. Обновлять README при изменении запуска или возможностей.
- Перед защитой повторно сверить пояснения со всем итоговым кодом. Ключевые
  алгоритмы описывать связными фразами, пригодными для устного объяснения.
- После завершения функций и итоговой проверки напомнить пользователю о
  PDF-инструкции со скриншотами и подготовить её по окончательному интерфейсу.
  План незавершённых задач хранить в docs/ROADMAP.md.
